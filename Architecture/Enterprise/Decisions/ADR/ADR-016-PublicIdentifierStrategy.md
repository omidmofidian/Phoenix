# ADR-016: Public Identifier Strategy

## Status

Accepted

---

## Context

Phoenix is expected to evolve from a modular monolith toward a Service-Oriented Architecture (SOA) and potentially Microservices.

Using sequential database identifiers directly in APIs introduces several problems:

- Information leakage
- Difficult data exchange between services
- Poor interoperability with external systems

Using UUID as the primary key, however, reduces database performance due to larger indexes and slower joins.

---

## Decision

Phoenix adopts a dual identifier strategy.

Each entity shall contain:

- Internal Identifier
- Public Identifier

### Internal Identifier

Purpose:

- Database primary key
- Foreign key relationships
- Internal joins

Type:

```text
BIGINT GENERATED ALWAYS AS IDENTITY
```

### Public Identifier

Purpose:

- REST APIs
- External integrations
- Event messages
- Future distributed systems

Type:

```text
UUID
```

Generated by:

```text
gen_random_uuid()
```

---

## Example

```sql
id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

public_id   UUID NOT NULL DEFAULT gen_random_uuid()
```

Unique Index

```sql
CREATE UNIQUE INDEX ux_table_public_id
ON table_name(public_id);
```

---

## Consequences

### Advantages

- High database performance
- Global uniqueness
- API security
- SOA readiness
- Microservice readiness
- Easier data synchronization

### Disadvantages

- One additional column per table
- Slightly larger storage footprint

---

## Applies To

This decision applies to every entity in Phoenix.

- Exchange
- TradingBoard
- Sector
- Industry
- Company
- Instrument
- InstrumentListing
- TradingCalendar
- DailyMarketData
- CorporateAction
